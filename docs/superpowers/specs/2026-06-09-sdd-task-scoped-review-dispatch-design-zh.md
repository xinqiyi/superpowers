# SDD 任务范围审查分派

使 subagent-driven-development 的每任务审查更便宜、更快但不削弱它们，通过将每任务审查提示限定到任务范围并停止冗余工作——同时最终分支审查保持广泛。

## 问题

SDD 中的每任务代码质量审查者例行对单任务差异做分支审查级别的工作。来自两个真实本地 SDD 会话的证据：`a1a6719a-6109-453a-9933-34ae396f5bae`（sen-core-v2）和 `0cc1a12d-9984-4c35-8615-9d42dadb2c47`（serf），都在 `~/.claude/projects/` 下：

- 在 sen-core-v2 会话中，7/8 的质量审查者运行了仓库级别的 grep；最昂贵的在约 200 秒内运行了 50 多个 Bash 命令。跨两个会话，质量审查者成本是同一任务上 spec 审查者的 4-8 倍。
- Spec 审查者，其提示包含"Only read files in this diff. Do not crawl the broader codebase"，保持紧凑：6-16 次工具调用，14-65 秒。
- 没有审查者自主运行重型测试。观察到的每个包级别或重复测试运行都是由控制者编写的提示明确请求的（"check all uses"、"run tests if useful, especially race-focused ones"、"does anything else read `Meta()`？"）。

根本原因，按影响排序：

1. **每任务质量提示继承了一个合并就绪审查。** `code-quality-reviewer-prompt.md` 委托给 `requesting-code-review/code-reviewer.md`，后者询问架构、可扩展性、安全性、生产就绪性，并以"Ready to merge？"结束。那个框架在一个任务差异上许可了分支级别的广度。Spec 提示的差异范围保护从未被继承过来。
2. **控制者没有关于编写审查者提示的指导**，因此它发明了开放式指令（"check all uses"），审查者按字面解释。
3. **管道中的重复工作。** 质量模板的"Plan alignment"维度重新检查了 spec 审查者刚刚验证的内容。审查者重新运行实施者已经运行（并报告，带有 TDD 证据）的测试套件，针对相同代码。
4. **每任务和最终审查共享一个模板**，所以没有任何地方表示"每任务窄，最终广"。

一份实地报告（`~/2026-06-09-code-quality-reviewer-scope-budget-issue.md`）首次标记了这个问题。它引用的会话和标题数字无法验证，但其定性诊断已针对两个真实本地会话确认。对它的一个修正：横切审计（锁顺序、更改的契约）有时是*正确的*审查方法——修复必须将广度关在陈述的具体风险后面，而非禁止它。

## 目标

- 每任务审查限定到任务范围：diff 优先阅读，合理的范围扩展，无冗余测试运行。
- 最终全分支审查保持其当前广度。
- 不减少审查捕获的内容。

## 非目标 / 明确保留

- **完全重新审查保留。** 当审查者在修复后重新审查时，它仍然以完整阅读广度审查整个任务。（它不重新运行实施者刚刚在修改后的代码上运行的测试。）这有意拒绝了实地报告的"重新审查预算"补救措施：其最差引例的成本（重新审查运行 `-race` 和 `-count=100` 循环）由下面的测试预算限制，而非通过缩小重新审查者的阅读范围。
- ~~**两个审查阶段保持分离。** Spec 合规和代码质量保持为独立的 subagent，串行把关。不合并。~~ **被下面的成本迭代取代**：实时评估经济学显示每次分派开销主导成本，维护者将所有选项摆上桌面。每任务阶段现在是一个任务审查者带两个判定；独立的广泛最终审查保留。
- **协调器保持模型判断。** 不为审查设置强制模型层级，任一方面。
- **`requesting-code-review/` 保持不变。** 它保持为最终分支审查和临时审查的广泛模板。
- 判定顺序（spec 合规在质量之前报告）、修复和重新审查循环以及修复 Critical/Important 发现的要求不变。

## 成本迭代（启动后评估经济学）

在质量加固散文（证据规则、约束传递、原始输出）落地后，实时的前后运行暴露了成本回归：go-fractals 从 42.8 分钟 / 14.5M token（首个任务范围版本）上升到 69.9 分钟 / 32.2M（加固版本），同时达到基线平级质量（盲评 8.5 vs 8.5）。每 subagent 轮次分析将成本归因于，按顺序：廉价模型在多步骤工作上花费 2-3 倍的轮次（1197 次 subagent 轮次中 678 次是 haiku）、每分派开销（每个任务 3 次 subagent 启动，每次重新推导差异；协调器协调是花费的一半）、以及证据规则叙述。

- **迭代 1：** 轮次数击败 token 价格的模型指导（多步骤工作的中档底线）、可选的内联差异、引用而非叙述的证据、Important = 不能信任直到修复、仅对 Critical/Important 分派修复。结果：68.2 分钟 / 22.9M — token 下降 29%，挂钟时间持平；当措辞为可选时，控制者仅在 22 次审查分派中的 2 次粘贴了差异。
- **迭代 2：** 每任务 spec 和质量审查合并为一个 `task-reviewer-prompt.md`（一个审查者，一次差异阅读，两个判定；一次修复分派处理两种发现）；实施者在迭代时运行聚焦测试，在提交前运行一次完整套件。结果（go-fractals）：47.5 分钟 / 15.7M / $13.55 — 在每项指标上击败基线，盲评 9/10 vs 基线 7/10。
- **迭代 3：** 校准命名了阻止合并的可维护性损害（逐字复制、吞掉的错误、无断言的测试）作为 Important，Minor 发现必须粘贴到最终审查中进行分类；审查者怀疑扩展到实施者的设计理由（"按 YAGNI 保留"是声明，而非判定）；差异以文件形式交给审查者（`git diff > /tmp/sdd-task-N.diff`，重定向使其永远不会进入控制者上下文；审查者一次 Read 调用），因为粘贴到提示的指导未被采纳（11-17 次分派中 0-6 次），出于本地合理化的上下文经济学原因。
- **最终冻结配置（e355795），所有五个场景通过：** go-fractals 44.4 分钟 / 13.4M / $11.67（-32% 时间，-37% token，-27% 美元 vs 基线）；svelte-todo 62.8 / 19.7M / $15.76（-21% / -28% / -25%）；rejects-extra-features $1.31（vs $1.88）；spec-reviewer-flaws 持平；植入缺陷场景（v3：判断调用的公开标记透明度栏，名称承诺验证但从不执行的测试的 must-fix 栏）通过，缺陷被捕获并修复。

### 迭代 4-5（2026-06-10）：方差坦诚、结构修复、正面配方

相同配置的重新运行暴露了运行间方差（同一提示上 44.4→57.1 分钟；审查者逃生舱门胃口波动 1.0→6.3 次工具调用/审查），因此所有后续声明使用范围。go-fractals 上的五个并行实验变体加上对真实本地会话的转录挖掘（完整日志含负面结果：`evals/docs/experiments/2026-06-10-sdd-cost-experiments.md`）产生了最终配置：

- **已采纳：** 最终审查包（最终审查者 33→6 轮次，以控制者模型价格）；两个模板中必需的 `model:` 行（散文指导在会话中途衰减了一次，继承 opus 用于 17 次分派，+$5）；任务简报 + 报告文件（`scripts/task-brief`；保真度锚，适度的上下文节省）；`<git-dir>/sdd/progress.md` 中的进度台账（真实会话在压缩后重新分派了整个已完成的任务序列——约 22 个任务的 269 次分派）；全能最终修复者（一个真实会话的每发现修复波成本超过了所有任务）；范围限定修复测试；唯一的 SHA 范围附带名称（工作树/子模块安全）；分派组合配方和审查者命名风险预算（微测试：正面配方 3.0 转录值 vs 禁止 4.4 vs 控制 3.6——禁止可能适得其反；参见 `2026-06-10-positive-instruction-redesign-design.md`）。
- **测试并拒绝：** 控制者轮次批处理和并行调用管道化（控制者每条消息恰好发出一个工具调用——每次运行中 0 条多工具消息；其轮次的 46% 是思考/叙述，一个提示免疫的底线）；后台分派管道化（机制 7/28 被采纳，但收益低于这些场景上 ±6 分钟的噪音底线）。
- **最终验证配置（b81f35b 系列），所有关卡通过：** go-fractals 54.1-54.7 分钟 / 14.4-16.6M / $12.81-14.31（基线 64.9 / 21.2M / $16.07）；svelte-todo 55.0 分钟 / 19.3M / $14.99（基线 79.7 / 27.3M / $20.98）；植入缺陷通过 / $2.77。跨所有 8 次相同设计 fractals 运行：44.4-57.1 分钟 / 13.4-20.0M / $11.67-14.84——最差抽签在每项指标上击败基线；典型中档节省约 20-25%。

## 设计

### 共享原则：不要在未更改的代码上重新运行测试

实施者的报告包括测试结果和 TDD RED/GREEN 证据，针对恰好正在审查的代码。审查者通过阅读验证。审查者仅在阅读提出特定怀疑且没有现有运行能回答时才运行测试——然后运行聚焦测试，而非套件。在审查者 subagent 为只读的 harness 上（例如，Antigravity 将审查者模板映射到 `research` 类型，后者无命令访问权限），审查者改为在其报告中命名它将要运行的测试。

在修复后，实施者重新运行覆盖修改后代码的测试；重新审查者不重复该运行。今天没有任何内容强制执行这一前提：`implementer-prompt.md` 仅描述了初始实现-测试-提交流程，没有修复迭代说明。因此，此 spec 还向 `implementer-prompt.md` 添加：在修复审查发现后，重新运行覆盖修改后代码的测试，并将结果包含在修复报告中。

此原则出现在两个审查者提示、实施者提示和控制者指导中。

### 1. 新文件：`skills/subagent-driven-development/code-quality-reviewer-prompt.md` 变为自包含

停止委托给 `requesting-code-review/code-reviewer.md`。每任务质量审查者获得自己的范围限定提示模板：

- **框架：** "You are reviewing one task's implementation for code quality。"一个任务范围的关卡，而非合并审查。
- **Spec 合规已确定：** spec 审查已通过；不要重新讨论需求或计划对齐。
- **保留的审查维度：** 代码质量（清晰度、重复、错误处理）、测试质量（真实行为，而非 mocks）、可维护性和现有的 SDD 特定检查（单一职责、独立可测试性、来自计划的文件结构、此更改贡献的文件增长）。**已放弃：** 计划对齐、安全/可扩展性/生产就绪维度、合并判定。
- **范围预算：** 从 `git diff BASE..HEAD` 开始；首先读取更改的文件；仅评估你可以命名的具体风险时才检查相邻代码。横切更改——锁顺序、更改的函数/API 契约、共享可变状态——是证明检查调用站点合理的合法命名风险。默认不爬取代码库。
- **测试预算：** 上述共享原则，另加：没有包级别套件、竞态检测器或重复/高计数运行，除非你先命名了特定的疑似不稳定或竞态。否则，在报告中推荐重型验证而非运行它。实施者报告的测试输出中的警告或噪声是发现——输出应该是原始的（实施者的自我审查也检查这一点）。
- **证据规则：** 审查者用文件：行证据回答每个 What-to-Check 项，而非简单的是/否。（在实时评估运行显示审查者通过了提示指向它们的缺陷后添加——一个可访问名称检查和一个临时目录清理检查都得到了不支持的"yes"答案，而缺陷就在被审查的差异中。）
- **只读规则** 以修剪形式保留：不改变工作树、索引、HEAD 或分支状态。当前模板中的 `git worktree add` 操作方法句子**不**带入此文件——差异范围的审查永远不需要另一个修订版的检出（与下面 spec 提示清理相同的理由）。
- **判定：** Strengths / Issues (Critical/Important/Minor) / "Task quality: Approved | Needs fixes。"

### 2. `skills/subagent-driven-development/spec-reviewer-prompt.md` 清理

- 移除 `git worktree add` 操作方法句子。只读规则保留；差异范围的 spec 审查永远不需要另一个修订版的检出。
- 解决仅差异保护与"独立验证一切"之间的张力：spec 合规通过阅读差异与需求进行判断。实施者的 TDD 证据覆盖"它能运行"——应用共享测试原则。
- 新的第三判定通道：无法从差异验证的需求（存在于未更改的代码中，跨任务）被报告为明确的"⚠️ Cannot verify from diff — controller should check X"项，而不是要么爬取要么静默通过。流程图的二进制的通过/失败菱形无法路由此内容，因此控制者指导（§3）定义了处理：⚠️ 项不阻止分派质量审查者，但控制者必须自行解决每个项（它持有计划和跨任务上下文）在标记任务完成之前；控制者确认是真实差距的项被视为失败的 spec 审查并返回给实施者。
- 将捏造的前提"The implementer finished suspiciously quickly"替换为基于事实的怀疑论：将实施者的报告视为关于代码的未验证声明。相同的不信任，无虚构事实。

### 3. `skills/subagent-driven-development/SKILL.md` 控制者更改

- **模型选择：** 将"Architecture, design, and review tasks: use the most capable available model"替换为判断指导——按选择实施者模型的方式选择审查者模型，按差异的大小、复杂性和风险进行缩放。"Task complexity signals"列表被重新范围化以明确其要点描述实施任务；审查者模型选择遵循相同的判断，因此窄差异审查不自动映射到"广泛代码库理解 → 最强大的模型"。
- **审查者提示构建**（红旗附近的新指导）：在分派审查者时，不要编写开放式指令（"check all uses"、"run race tests if useful"）而没有具体的任务特定原因；不要要求审查者重新运行实施者已经在相同代码上运行过的测试；不要为审查者预判结果（决不要指示审查者忽略或不标记特定问题——在审查循环中裁决可疑的误报）。每任务审查是任务范围的关卡——广泛审查发生一次，在最终全分支审查时。（预判规则在一次实时评估运行捕获控制者捏造了一个"计划禁止共享辅助函数"的声明并指示质量审查者不要标记植入的 DRY 违规后添加。）控制者还必须将绑定任务的 spec/设计的全局约束——版本底线、命名和复制规则、平台要求——包含在粘贴的需求中：一次实时运行交付了一个 `go 1.26.1` 模块底线，针对的是"Go 1.21+"设计，因为没有任何审查者见过该约束。并且控制者必须在每次分派上明确指定一个模型——省略的模型继承会话的（通常最昂贵的）模型，这静默地击败了模型选择。
- **处理 spec 审查者的 ⚠️ 项**（"Handling Implementer Status"旁的新指导）：控制者自行解决每个"无法从差异验证"的项，在标记任务完成之前；确认的差距作为失败的 spec 审查返回给实施者。
- **最终审查保持广泛，明确：** 最终全分支审查者分派节点获得一个显式的指向 `../requesting-code-review/code-reviewer.md` 的指针。（今天该模板只能通过每任务质量提示的委托访问；一旦该委托被移除，未引用的最终审查模板将被孤立。）集成部分中关于 `superpowers:requesting-code-review` 提供"the code review template for reviewer subagents"的说明更正为仅适用于最终审查。
- **示例工作流：** 示例中的质量审查者行更新为新的判定词汇（"Task quality: Approved"）；最终审查者的"ready to merge"行保留。
- 流程图拓扑不变；⚠️ 通道由控制者指导处理，而非新的图分支。

## 此修复不解决的问题（已知，已推迟）

Spec 审查者根据控制者粘贴的任务文本进行判断；它无法捕获控制者从计划中提取时丢弃的需求。这是"控制者提供完整文本"的架构属性，而非提示问题，超出此处范围。

## 验证

- Plugin 基础设施测试（`tests/`）仍然通过。
- 在更改前后运行 SDD skill 行为评估（`git submodule update --init evals`，然后按 `evals/README.md`）。具体来说：`sdd-go-fractals`、`sdd-svelte-todo`、`sdd-rejects-extra-features`（端到端 SDD，包括 spec 审查者的 YAGNI 关卡）和 `spec-reviewer-catches-planted-flaws`。
- 此更改暴露的已知评估差距：没有现有场景在单个 SDD 任务内植入代码质量缺陷并断言每任务质量审查者捕获它，也没有场景衡量每审查者探索成本（工具调用/grep 计数）。添加一个场景覆盖第一个差距（植入的单个任务质量缺陷 → 每任务审查者必须在最终审查前标记它）。对于探索成本，在前后评估转录之间手动比较审查者 subagent 工具调用计数。
